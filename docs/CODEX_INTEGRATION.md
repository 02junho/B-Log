# Codex 통합 검증 준비 (역할 B, 2026-09-09)

작업 브랜치: `codex/codex-pipeline-integration`. 기준은 main `407dc4d`이며,
PR #5의 어댑터 수정은 별도 리뷰 대상으로 유지한다.

## 완료한 사전 검증

`tests/codex-pipeline.test.ts`에서 합성 rollout을 공통 `parseSession` 입구에 넣고,
자동 판별 → 공통 스키마 → 청킹 → 태깅 → PortfolioView 빌더까지 연결했다.
태깅 runner만 테스트용 응답을 주입하며 실제 API·LLM·DB는 호출하지 않는다.

- 이벤트 순서와 ID, Codex 분석 등급, 사용자/AI/도구 통계 보존.
- 확인된 커밋 SHA가 포트폴리오 커밋 링크로 연결됨.
- 원문에 없는 인용은 타임라인·하이라이트에서 제외됨.
- 태깅 실패 시 1회 재시도 후 실패 청크가 반환되고 findings가 생성되지 않음.
  API는 `failedChunks`를 확인해야 하며 빈 포트폴리오를 분석 성공으로 발행하면 안 됨.

통합 테스트에서 다른 이벤트의 문장을 동일 청크 안에서 잘못 인용해도 통과하는 문제를
재현했다. `src/lib/pipeline/tag.ts`에서 인용을 이벤트별 렌더링 구간으로 제한하고,
빈 인용·렌더링 헤더·이벤트 경계를 가로지르는 인용을 제외하도록 수정했다.
P1 소유 태깅 코드 수정이므로 다음 PR에서 P1 리뷰를 요청한다. 스키마 변경은 없다.

기본 테스트 52개 통과, 선택 실로그 테스트 2개 제외. PR #5와 서로 다른 main 기반
브랜치이므로 PR #5의 테스트 개수와 합산하지 않는다.

## API가 준비되면 확인할 것

1. Codex 업로드의 source/fidelity와 정규화 이벤트·도구 통계가 CLI 결과와 일치하는지.
2. 잡 재시도·재개 시 같은 청크와 finding이 중복 저장되지 않는지.
3. 일부 태깅 실패를 잡 상태에 남기고 전체 성공과 구분하는지.
4. 검증된 인용의 이벤트·시간·커밋이 저장 및 조회 후에도 유지되는지.
5. 마스킹·사용자 검수를 거친 결과만 공개되는지.

위 항목은 준비용 체크리스트이며 API·웹 E2E 완료를 뜻하지 않는다.

## 후속: 긴 세션·부분 실패 검증

- 짧은 대화 뒤 긴 대화가 오면 병합 경로가 크기 검사를 건너뛰는 문제를 테스트로
  재현하고 수정했다. 청크 병합·분할의 길이 계산에 구분 줄바꿈도 포함한다.
  9,000자는 soft cap이며 단일 이벤트 자체가 큰 경우까지 강제 분할하는 변경은 아니다.
- Codex 입력에서 3개 청크를 만든 뒤 가운데 청크만 실패시키는 통합 테스트를 추가했다.
  재시도 횟수, 실패 청크 ID, 진행률, 성공 결과의 순서와 토큰 집계, 포트폴리오 반영을 확인한다.
- 청킹 수정도 P1 소유 코드이므로 PR 리뷰 대상이다. API 저장·재개·중복 방지 검증은
  백엔드 구현 후 별도로 진행한다.
- 후속 검증 결과: 기본 테스트 55개 통과(선택 실로그 2개 제외), 린트·타입 검사 통과.
